# Native messaging: the Chrome host-manifest standard, no per-extension code

Safira has no code for any particular extension or native app. `runtime.connectNative` and `runtime.sendNativeMessage` follow Chrome's native messaging standard on macOS: an app registers a host by writing `<name>.json` (`name`, `description`, `path`, `type: "stdio"`, `allowed_origins`) into `~/Library/Application Support/Safira/NativeMessagingHosts/`; Safira refuses an extension whose `chrome-extension://<id>/` origin the manifest does not list, starts `path` with that origin as its argument, and passes messages through its stdin and stdout as a 4-byte little-endian length and JSON (1 MB from the host). One process per port, ended when the port closes. An app that already registers its host for Chrome or Brave supports Safira by writing the same manifest into Safira's folder, and its extension stays a standard Chrome extension: Safira derives the same id from the manifest `key`.

Safira stays sandboxed, which shapes the rest. The entitlements add read-only exceptions for that folder in the user's real home (the sandbox's home is the container) and for `/Applications/` and `~/Applications/`, where hosts live inside their apps' bundles. A host runs inside Safira's sandbox, so it can reach the network as a client but not the user's files. A host that is sandboxed on its own without `com.apple.security.inherit` is killed by macOS at launch under a sandboxed parent; Safira reads the host's entitlements from its code signature first and refuses it with an error that names it. Such apps (1Password's browser helper today) need an unsandboxed host launcher or a host that inherits the sandbox; that choice is open.

This replaces the first plan of unit 3, a relay from Safira to Verrou's local TCP bridge, which put one app's protocol, port and bundle id in Safira.
