# Extensions via WKWebExtension, Verrou first

Supersedes ADR 0004. The extension spike of 2026-11-15 loaded Verrou's unchanged Manifest V3 extension into the system's public `WKWebExtension` API on macOS 27: its manifest parses with no error, its module service worker, storage, alarms, localisation, action popup and content scripts in both worlds run, and `runtime.connectNative` reaches the app. The go/no-go that ADR 0004 deferred is therefore a go, within ADR 0001: no SPI, no WebKit fork.

Extensions come in five units, Verrou first: a host per Profile with loading from a folder, the action button and popup, native messaging relayed by Safira to Verrou's local bridge (Safira only ever sees ciphertext), the Extensions settings pane, then passkeys. Each Profile owns one `WKWebExtensionController` bound to its own data store, so extension storage follows the Profile boundary (ADR 0002); a Private window runs no extension. An extension is installed once for the app and turned on per Profile, and each Profile pairs with Verrou on its own. WebKit ignores the manifest `key`, so Safira derives the identifier from it, as Chrome does, to keep `runtime.id` and the extension's storage stable.

The accepted risk is the keychain. Verrou keeps its pairing key as a non-extractable `CryptoKey` in IndexedDB, and WebKit wraps such keys with a per-app "WebCrypto Master Key" in the login keychain. An ad hoc signed build may prompt for it after every rebuild. Before Verrou pairs in Safira, a Developer ID-signed copy must read a persisted key back after a relaunch without a prompt. If it cannot, keeping the channel key extractable in Verrou's `storage.local` is the owner's call, not an implementation choice.
